# 项目 Agent 约束

将本文件中适用且已填写的内容纳入工程规则；不要替换平台生成或托管的 `AGENTS.md`。本文件是模板，`null`、空数组和 `UNSET` 都表示尚未配置，不能当作通过或默认设备选择。

## 权威规则与适用范围

- 使用 CANNBot 时，以当前任务实际选中的平台入口及其工作流、角色、精度/性能标准、确认节点和状态记录为准。本文件仅补充工程反例与核查点，不能覆盖上述规则。
- 平台已有需求、实验或状态文件时，项目信息按其原生格式记录。下文的 `project.json`、`acceptance.json`、`evidence.json` 仅为独立使用示例；共存时可用 `supplement.md` 引用权威证据，不能另设同名验收结论。
- 沿用平台要求的派发格式和串并行安排。补充证据写入允许的文档或附件，不额外创建角色，不向受限的派发模板塞入另一套任务书。

## 任务与边界

- 本次任务 owner、目标分支、配置和已授权动作以 `project.json` 及用户最新指令为准。先读已有授权；无需重复确认已授权的常规工作。
- 在 `references.json` 记录本次允许的参考来源及只读范围；清单缺项不能推翻用户已有授权。按已确认的 `integration.mode` 决定修改位置：外部插件任务不覆盖 native 安装目录；原生框架开发则在授权的源码树内修改并验证，不能把参考副本当部署目标。
- oracle 仅用于测试。生产路径不可偷偷进入 CPU、简化数学实现或测试 oracle。
- 物理设备、SOC、模型、端口必须来自本次有效配置。未知值明确报错，不能继承历史任务的设备和路径。
- 同时工作的 agent 明确文件与 case owner；保留他人的修改。已冻结源码、启动参数、计时脚本和数值规则须按任务约束保护。

## 实施与验证

- 修改前查找相关事故条目，写明证据来源、假设、影响范围和回归用例。历史猜测与已证实原因分开记录。
- 精度 oracle、容差、错误域和统计规则先于测量冻结；平台已有标准时直接遵循，不能改用本包通用 atol/rtol 示例。更改数学语义或 dtype 时按权威流程更新合同；不能为已观察失败事后放宽阈值。
- 候选开关只在一个入口定义，部署、探针与测试共享；验证配置真正到达生产路由及对应产物，不能仅更新 probe。
- 构建复用必须验证源码、配置、工具链与最终产物身份。复用成功只提供编译证据。
- 分阶段运行安装、编译、设备探针、服务探针和正式服务。是否执行探针由任务约定；规定必须通过的探针失败时立即停止后续阶段。
- 输出与错误实时可见且完整落盘，保留原始子进程退出码。超时、中断、清理不完整单独记录。
- 仅清理当前任务创建且可证明归属的进程组、文件和构建目录；不按进程名全局杀进程，不重置设备或清理他人缓存。
- graph capture 与 replay 分开验证。保持需要的地址与缓存生命周期；诊断同步、计时和 host 回读不能无意进入生产捕获路径。

## 证据与交付

- 独立使用时可在 `evidence.json` 分别记录 source、host、compile、device、graph_capture、graph_replay、quality、performance。共存时保留平台原始状态及证据；例如 `conditional_pass` 不得改记为 `pass`，格式检查也不是平台验收。
- `pass` 必须有对应工件和明确理由。缺设备、用户未授权测量、片段缺失都不等于通过；不适用必须给出与任务相关的原因。
- source/CPU/编译通过不等于设备执行通过，readiness 不等于模型质量或端到端性能通过。算子局部加速不能直接外推整轮收益。
- 实验绑定基线和候选版本、argv、输入、计时和统计口径。预先约定必测场景，不能仅报告改善场景而遗漏回退。
- 用户已有完整 benchmark 时优先离线解析已保存工件；报告未知分母、缺失记录、错误记录、run 覆盖率和计分差异。
- 实测事故才写为现场事实。主机反例、理论推导和仿真结果带清晰标签。最终交付列出变化、验证证据、未完成层级及可复现命令。
