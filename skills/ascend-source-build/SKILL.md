# 源码、构建与实际生效

用于存在母源、生成器、独立算子库或插件路由的 Ascend 工程。先读取目标工程当前任务约束和入口；从其配置取得 SDK、SOC、Python 环境及允许的参考源码，不继承历史机器参数。

## 五项关键判断

1. **绑定当前源码与候选路由。** 记录当前提交、相关源文件摘要、实际调用点、算子名称及 ABI。历史 profile 的热点只有在当前路由仍然存在时才支持本轮改造。多分支经验先归并到来源提交，再区分已替代策略；分支名字和旧报告日期不是产物身份。

2. **追踪完整生成链。** 列出母源、生成器输入、生成输出、编译库、加载路径和最终配置开关。修改生成输出前确认是否会被再生成覆盖；维护已有冻结源或身份检查时，不为了让测试通过而同步改掉预期摘要。若任务要求更换基底，显式更新版本合同与来源。

3. **核对硬件语义与 ABI。** 对照目标 SDK 中的接口声明核实数据类型、对齐、shape、步长、workspace 和调用约定。尾块、有效长度和物理存储布局分开处理。涉及搬运或同步时标明每个缓冲区的生产者、消费者及复用时点；只插入屏障不能证明跨核所有权正确。

4. **按风险形成证据链。** 先做能够隔离变更的源码检查、CPU 独立参考和 CANN 构建；设备运行须处于任务授权范围。构建成功仅证明该构建环境接受源码，CPU-debug 不证明 NPU 执行或图捕获正确。依赖版本无法核实时记录缺口，不用其他 SOC 的成功记录补齐。

5. **交付实际启用的变更。** 在项目正式入口检查配置确实传播到插件和对应算子，保存库路径、版本与路由证据。探针与正式服务若各自维护候选开关，应收敛到共享配置；已有服务进程加载旧库时，不能用新文件存在作为生效证据。遵守项目的安装机制，不覆盖用户原生框架源码来掩盖插件接入问题。

## 最小交付信息

给出改动源身份、构建命令与真实退出码、产物加载路径、启用方式、已通过和未执行的验证层。若尚未在目标设备运行，明确只交付到哪一层；不把编译或导入成功写成性能、质量验收。
