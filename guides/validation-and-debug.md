# Ascend 分层验证与故障定位

每层证据只回答本层问题。按当前任务声明验证层及依赖，不要求每个项目依次执行全部层；某层通过不能替代其他层的证据。

## 分层验收表

| 层级 | 要回答的问题 | 最低证据 | 不能推导出的结论 |
| --- | --- | --- | --- |
| 源码与路由 | 改动实际被调用吗，保护路径还在吗 | commit、配置、源指纹、调用点和派发检查 | 设备完成或提速 |
| CPU / 独立 oracle | 数学、边界和错误传播符合预声明合同吗 | 独立参考、形状与输入覆盖、误差和失败输出 | NPU 舍入、异步和硬件时序正确 |
| CANN 编译与链接 | 当前 SDK/SOC 能编译、符号与 ABI 一致吗 | 编译器与 SDK 版本、完整构建退出码、产物身份 | NPU 执行正确 |
| 仿真 / CPU-debug | 完整核和协议在该模型中成立吗 | 所有相关 actor、越界与数值检查、模型限制 | 目标芯片的实际性能 |
| NPU 原语与完整算子 | 设备真正完成并给出正确输出吗 | 完成同步、输出、状态、输入完整性、真实 rc | 完整模型质量或服务稳定 |
| 图捕获 | 目标路径能捕获吗 | 捕获配置、buffer 地址、符号和描述符 | 回放正确 |
| 图回放 | 固定地址更新输入后仍产生正确的新结果吗 | 多次同址变输入、输出对拍、容量与生命周期 | 真实服务所有调度状态已覆盖 |
| 服务与生命周期 | 请求完成、失败和清理都可靠吗 | 实际 endpoint、请求结果、owned 资源释放 | 数据集准确率或负载性能 |
| 模型质量 | 固定评测合同下质量达标吗 | 输入/模型/PT/评分规则身份、全部结果和覆盖率 | 不同输出预算或评分规则下也达标 |
| 端到端性能 | 指定场景相对配对基线有净收益吗 | 同参数整轮 wall、吞吐/延迟、变异与异常说明 | 未测长度、batch 或部署也达标 |

未执行写 `not_run`，失败写 `fail`，部分证据写清覆盖；依赖缺失不能改成通过。源项目的 checkpoint 状态会同时保留主机通过与设备/质量未验收，见 `docs/checklist.md@7047ce36`、`docs/standalone_perf_profile_20261112.md@fb1a5078`。

本表细分了诊断范围；模板用八个 gate 记录最小证据。仿真可在 `host` 的工件与 reason 中单独注明，服务执行可在 `device` 中注明覆盖范围；它们各自仍不能代替真实硬件精度或质量验收。复杂项目可增加独立 gate，并相应扩展校验工具。

## 数学合同要覆盖完整输出链

把存储类型、操作数类型、累加类型、归约顺序、舍入与转换位置分别记下来。量化等级/metadata、旋转域、partial、softmax 状态、合并和最终输出之间的边界可能比单个误差指标更关键。

局部代理更好，不保证最终 attention 输出或模型准确率更好。两个 partial 提前舍入后再合并，与先高精度合并再舍入可以产生不同结果。独立 oracle 必须覆盖完整数学链及必要错误域；生产实现不能导入测试 oracle 当作隐藏回退。对于超出支持范围的输入，用明确错误或预先定义的正式路径处理，不吞错后换算法。

测试同时检查正常输入、尾块、特殊浮点、非法 metadata、输入不被意外修改以及首个错误是否保留。授权的新数值合同不应被已失效的旧逐位目标否决；新容差也不能在看过候选结果后放宽。

依据：`docs/official_math_v4_20261021.md`、`docs/head_clip_alignment_20261023.md`、`docs/fp32_dequant_precision_20261023.md@fdb8eba9`。

## 阶段与状态不能靠形状猜

一个很短的 query 可能仍是真实 prefill 续块。源工程曾把与 speculative decode 等宽的 prefill 误分类，读取了尚未提交的 SSM/conv 状态；只修读取位置仍会把最终状态写错，污染下一轮 decode。

因此缓存/图适配至少验证：真实执行阶段、已提交状态、accepted/discard mask、最终发布位置、下一轮读取、同页与跨页、命中与未命中、dummy/capture/replay。阶段应来自框架协议，不能用 prompt 总长度或测试集名称代替。修正真实 prefill 的图选择可能有实际开销，需要如实记录，不能宣称“所有步骤零开销”。

图观测器还应核对真实 forward 签名：某些算子写显式输出 buffer 并返回 `None`，某些预处理通过 `inputs_embeds` 而非 `input_ids`。观察代码必须适应真实协议，不能改生产输入去满足观察器假设。

依据：`docs/gdn_prefill_state_20261028.md@fdb8eba9`、`docs/aisbench_stable.md@f96820f1`、`docs/service_precision_round_20261105.md@ea46d233`。

## 内核与诊断辅助代码也有 ABI

Ascend 混合引擎代码不能默认同名 C++ 类型在 AIC/AIV 编译中的布局一致。源工程的诊断 helper 含引擎相关成员，却产生同名 weak 函数，链接后共用一个布局版本，导致另一个引擎按错误偏移读取。

这类问题要用产物证据定位：保留各引擎目标文件，比较符号、可见性、布局与反汇编，再验证最终混合链接对象。需要引擎/翻译单元隔离的 helper 应显式隔离，不能依赖“采样关闭所以不会出错”。构建指纹应包含相关头文件，确保修复真正重编译。

本地反汇编能证明本地 ABI 缺陷；没有现场同一产物就不能宣称已精确符号化现场 PC。链接通过仍需设备复验。

依据：`docs/internal_recorder_linkage_20261113.md@fb1a5078`。

## 事故记录应把观测、解释、修复分开

记录最早错误、发生阶段、源/配置/产物身份、复现条件与完整 rc。HCCL/copy/worker 异常可能是前序设备失败的后果，不能根据最后一条报错直接归因。kernel 名字后缀不自动对应模型层号；启动返回也不是设备完成。

显式诊断同步会改变异步和图行为。诊断模式成功只能说明该模式成功，正常模式稳定性仍需原条件验证。保存原失败证据，新增修复记录，不倒改历史。CPU 反例和理论判断可登记为研究证据，不能伪装成新真机事故。

依据：`docs/offload_guard_incident_20261110.md@59f08592`、`oscar_ascend_agent_start.md@7047ce36`。
